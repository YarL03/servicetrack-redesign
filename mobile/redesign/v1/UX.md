# UX-спецификация мобильного приложения «Сервис Трек»

## Границы решения

Это редизайн рабочих сценариев исполнителя, с вариантом переписки исполнителя и менеджера. Авторизация, администрирование пользователей и конструктор форм в эти 24 макета не входят. Данные примеров: восемь доступных заявок, пять активных назначенных, две неназначенных и одна выполненная. Чаты показаны для трёх назначенных заявок. Счётчики активных групп пересчитываются при локальном завершении работы.

## Навигация

«Мои» — стартовый раздел; «Все» сохраняет общий реестр, «Чаты» содержит разговоры по заявкам, «Профиль» — историю, уведомления, настройки и отправку. Центр уведомлений также открывается колокольчиком из основных разделов. Существующий раздел «Сообщения» сейчас относится к уведомлениям; полноценная переписка — новая функциональность, её нельзя считать уже имеющимся API.

У каждого варианта есть одни и те же точки входа: поиск над списком, фильтры рядом, нажатие карточки открывает контекст, кнопка «Продолжить работу» явно ведёт к форме. Все три варианта сравниваются на одном наборе данных. Предпочтительный вид списка запоминается между переходами в открытом прототипе; в продукте — настройка пользователя.

В адресном виде видимый переключатель «Группировка заявок» предлагает «По улице» и «По улице и дому». Первый вариант объединяет дома одной улицы и сохраняет дом/квартиру в каждой строке заявки; второй создаёт отдельную группу на дом. По умолчанию выбран второй вариант. Переключение применяется сразу и запоминается в localStorage. Возврат из заявки сохраняет выбранный режим, раскрытые группы и прокрутку. В демонстрационных данных две заявки на Лермонтова находятся в домах 18 и 20; счётчики и группы строятся по текущим активным назначениям, без пустых фиксированных адресов.

Группировать по адресам нужно по нормализованным идентификаторам города/улицы и значениям дома/корпуса/строения; одинаковые названия улиц разных городов не объединяются. Заявки без адреса получают отдельную группу «Адрес не указан». Группировка не сортирует точки по геолокации и не обещает оптимальный маршрут. Доработка — `onRevision`, а не дополнительный серверный статус. Она показывается отдельно от обычных готовых заявок, чтобы счётчики не дублировались.

Внутри исполнения нижняя глобальная навигация уступает место одной основной кнопке. «Назад», список этапов и чат остаются доступны. Возврат из чата сохраняет позицию и значения формы. Системный Back в реализации следует стеку; жесты не являются единственным способом перехода.

## Поиск и фильтры

Одна строка принимает ID, внешний номер, адрес и имя абонента. Поиск из «Мои» ограничен назначенными активными, из «Все» — доступным реестром, из истории — завершёнными; область подписана и меняется явно. В строке остаётся запрос, в фильтрах — выбранные условия. Фильтры вступают в силу одной кнопкой; при закрытии без применения прежний набор сохраняется.

В прототипе результат локальный и мгновенный. Для сервера: задержка ввода около 250–350 мс, отмена предыдущего запроса, защита от устаревшего ответа, сохранение запроса/области/фильтров при возврате. Поиск по номеру может давать точное совпадение первым; нельзя подменять ID нечётким совпадением. Удаление номера в поле должно немедленно убрать прежний результат.

| Состояние | Поведение |
| --- | --- |
| Нет запроса | Недавние запросы и короткое объяснение поддерживаемых полей |
| Загрузка | Нейтральные скелетоны строк; не показывать прежние результаты как актуальные |
| Пусто | Запрос остаётся, доступны смена области и сброс фильтров |
| Ошибка | Понятное сообщение, «Повторить», сохранение условий |
| Без сети | Только сохранённые доступные пользователю заявки, заметная подпись области данных |
| Результат больше страницы | Продолжение списка с устойчивой сортировкой, счётчик из того же источника |

Состояния загрузки/сетевой ошибки поиска описаны для реализации; отдельного серверного запроса у макета нет. Поля текущего API фильтров не доказывают наличие серверного полнотекстового поиска; его контракт требуется согласовать.

## Исполнение: что упрощается

| Точка | Текущее поведение по коду | Предложение |
| --- | --- | --- |
| Начать новую работу | Длинная карточка, кнопка после подробностей | Краткий контекст и закреплённая кнопка, подробности раскрываются |
| Продолжить | Для IN_PROGRESS уже есть прямой переход в форму | Явная карточка продолжения с адресом и названием текущего этапа |
| Понять объём | Постраничная форма и пагинатор | Именованные этапы, признак заполненности, ссылка к полю с проблемой |
| Внести данные | Разные динамические типы, предварительное сохранение | Единая типографика полей; камера/сканер рядом с нужным полем; подсказка формата |
| Завершить | Кнопка «Завершить» на последней странице | Сводка фактических данных, переход к пропуску, явная отправка |
| Решить вопрос | Телефон менеджера в карточке | Чат из заявки и формы без потери черновика |

Сводка — дополнительный осознанный шаг для снижения ошибочных завершений; обещания «меньше кликов во всём процессе» нет. Для коротких шаблонов объём сводки можно уменьшить. Успех оценивать по времени поиска заявки, доле завершений без возврата на доработку, потерям черновиков и времени от вопроса до ответа. Численные улучшения требуют наблюдения за работой пользователей.

### Динамические формы

Три показанных этапа — конкретный пример. Renderer обязан использовать серверные `sortOrder`, `availableForEdit`, `availableForRoles`, `availableForStatuses`, `mandatory`, `editable`, `forWebOnly`, `maxFilesAllowed`, `availableFileExtensions`, `needToPreSave` и тип поля.

- Текст и число: постоянная подпись, подходящая клавиатура, единица измерения, ошибка рядом. Для десятичных чисел учитывать запятую. Read-only поля не выглядят доступными для редактирования.
- Дата: системный picker с явной датой и локальным временем. Штрихкод: сканирование с подтверждением распознанного значения и ручным вводом.
- Фото/видео: камера либо выбор, превью, количество, удаление до отправки, сохранение назначения файла.
- Аудио: таймер и индикатор записи, явные остановка/прослушивание/удаление. Пока запись активна, нельзя терять её переходом на другой этап.
- Файлы и MULTIPLE: имя, тип, размер, локальная доступность, ограничения шаблона, ошибка конкретного файла.

Форма может иметь ноль этапов, много этапов или только read-only поля. Пустой шаблон требует понятного сообщения и действия согласно существующему workflow. Переход к более позднему этапу не обходит обязательные поля и правила предварительного сохранения. Если этап требует подтверждённого сохранения, кнопка называется «Сохранить и продолжить», а при ожидании — «Ожидает подтверждения»; локальное автосохранение не отменяет этот барьер.

### Черновик и отправка

«Сохранено на устройстве» появляется только после успешной локальной записи. В ошибке хранилища не обещать сохранность. Проверка перед завершением берёт данные из того же черновика и показывает обязательные пропуски. До отправки текст и файлы могут быть исправлены. После постановки завершения в очередь форма блокируется, статус заявки остаётся IN_PROGRESS до подтверждения EXECUTED.

Неудача конкретного файла не должна повторно загружать уже подтверждённые вложения. «Исправить данные формы» должна отзывать неотправленное завершение до открытия редактора. Исчерпанный бюджет retry не обходится нажатием общей кнопки. Конфликт формы показывает серверные и локальные различия, не удаляет локальные файлы и требует повторной проверки. Нельзя обновлять UI чужой сессии поздним ответом.

Недопуск: обязательное фото уведомления, необязательное фото акта, дата/время, комментарий до 400 символов. Формулировка результата зависит от подтверждения отправки. Нельзя выдавать локальную операцию за синхронизированную.

## Чат по конкретной заявке

Рекомендуемый вариант — один рабочий диалог заявки. Менеджер и исполнитель видят номер, адрес и вид работ в закреплённой строке. Смена роли в панели каталога демонстрирует обе стороны одной переписки; интерфейс участника использует одни и те же принципы. Если в заявке несколько исполнителей, сервер должен определить состав участников явно; вопрос о группе или отдельных диалогах является продуктовым решением перед реализацией.

Нижняя вкладка «Чаты» и кнопка чата в заявке ведут к одной истории. Push открывает конкретную заявку и сообщение; badge означает непрочитанные сообщения, а не количество заявок. Центр уведомлений собирает события заявок, чатов и сервиса в разные категории; полная переписка остаётся в чате. Правила отметок, доставки, счётчиков и возврата описаны в [спецификации уведомлений](NOTIFICATIONS.md).

### Текст и файлы

Черновик сообщения привязан к ID заявки. Вложения из соседнего диалога не переносятся. Перед отправкой пользователь видит имя, размер, тип, количество и может удалить файл. Источники: камера, галерея, документ, видео, аудио. Предлагаемые лимиты для обсуждения — 25 МБ на файл и 5 вложений за отправку; реальный allowlist и лимиты задаёт сервер.

Состояния сообщения: подготовка → в очереди → отправка/прогресс → доставлено → прочитано (только при серверном receipt). Ошибка не убирает сообщение и локальную копию, предоставляет адресный повтор. Повтор использует тот же clientMessageId, чтобы не создавать дубликаты. «Доставлено» означает принятие сервером, не прочтение человеком. Прототип имитирует доставку и очередь, не показывает фиктивный статус «прочитано» для новых сообщений.

Вложения чата и обязательные материалы формы — разные сущности. Сам факт отправки фото менеджеру не заполняет поле формы. Будущее действие «Добавить в материалы заявки» возможно только с выбором целевого поля и проверкой прав/лимитов. Удаление или отсутствие локальной копии файла должно быть видно; без сети доступен только скачанный файл.

### Необходимая серверная часть

Нужны: разговор по requestId, участники и их права, пагинация истории, сообщения с clientMessageId, загрузка/скачивание файлов и receipts, количество непрочитанных, уведомления. Авторизацию проверять при чтении и скачивании, URL вложений — с ограниченным сроком. При переназначении заявки политика доступа к прошлой переписке должна быть определена явно. Выход из аккаунта очищает локальные данные его области; чужие диалоги не должны попадать в кеш следующей сессии.

Для мобильной интеграции: durable local file store до enqueue, очередь с идемпотентностью, загрузка файлов до отправки сообщения, отмена и повтор с сохранением локальной копии, offline-история и согласование после reconnect. SSE/WebSocket или polling — отдельное техническое решение, не часть визуального макета.

## Доступность и адаптация

Минимальная проверяемая ширина — 320 px, основной холст — 390 × 844. Базовые действия имеют область от 48 px. Контент прокручивается, кнопка не перекрывает последнее поле. В продукте учесть safe area, IME/KeyboardAvoidingView, большой системный шрифт и уменьшение движения. Статусы отличаются текстом и пиктограммой, не одним цветом. Поля имеют видимые подписи; ошибки привязаны к полю, состояние отправки озвучивается умеренно. Нужны реальные проверки TalkBack/VoiceOver, клавиатуры и поворота устройства при переносе в Expo.

## Что проверить с пользователями

Дать 5–7 исполнителям одинаковые задания на A/B/C: найти квартиру в доме, вернуться к начатой работе, найти недопуск, исправить фото после замечания, отправить файл менеджеру без сети. Сравнить время и ошибки, спросить, какой список нужен утром и на объекте. Отдельно проверить с менеджером входящие чаты нескольких заявок. По результатам выбрать основной вид и правила уведомлений, не добавляя все варианты как равноправные обязательные экраны.
